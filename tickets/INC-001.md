## Issue
Sending the same POST /transaction request repeatedly with reference_id
TXN-2001 returned 201 Created every time. Only the first request should
succeed; repeats should be rejected with 409 Conflict.

## Impact
- Customer is debited multiple times for one payment. In testing, 6
  identical requests debited Rs 3000 instead of Rs 500 (balance 7000).
- Any network retry or double click in production causes double billing.
- Affects every transaction and involves money, so priority is high.

## Steps Taken
1. Reproduced in Postman: identical POSTs all returned 201.
2. Ran pytest: test_duplicate_reference_id failed (assert 201 == 409).
3. Pushed the branch: CI (GitHub Actions) failed on the same test.
4. Queried payments.db: 6 rows with reference_id TXN-2001, balance 7000.
5. Inspected the table definition: reference_id has no UNIQUE constraint.

## Root Cause
The UNIQUE constraint on transactions.reference_id was missing from
schema.sql, so the database accepted duplicates and the application had
no second check.

## Resolution
Restored the UNIQUE constraint on transactions.reference_id in
schema.sql, deleted the corrupted payments.db and recreated it from the
fixed schema. Verified:
- pytest: 9 passed (test_duplicate_reference_id now passes)
- Postman: first POST returns 201, repeat POST returns 409 Conflict
- Database: one row per reference_id, balance debited once

## Preventive Action
- test_duplicate_reference_id runs on every push via GitHub Actions, so
  removing the constraint again fails CI before it can be merged.
- All changes go through a pull request, never directly to main.
- Note: schema.sql changes do not alter an existing database file
  (CREATE TABLE IF NOT EXISTS). After a schema change the database must
  be recreated or migrated, otherwise the old table definition stays.
